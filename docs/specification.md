# three-layered-scene-editor 仕様案

更新日：2026-11-17 / 状態：相談用ドラフト（未実装）

## 1. 目的と要求

既存のメインビジュアル画像を少数のPlaneへCamera Projectionで投影し、カメラ移動によって視差のある2.5D表現を作るローカルのブラウザー編集ツール。

- Vite + TypeScript + Three.jsを使用する。
- ジオメトリはPlaneGeometryに限定し、全体で10枚未満を想定する。
- Planeの追加・削除、位置・回転・サイズを編集する。
- PerspectiveCameraの位置・回転・FOVを編集する。
- 基準カメラから元画像を各Planeに投影する。
- 元画像とレンダリング結果を比較する。
- カメラの子として十分遠くへ配置する背景Planeを扱う。
- MeshBasicMaterialを基本とし、OPAQUEとBLENDを扱う。
- JSONで投影設定を含む編集データを保存・復元する。
- GLBでは投影結果をUVテクスチャにベイクし、カメラとともに書き出す。
- GLBの表示は独自シェーダーに依存させず、標準的なマテリアルで再現する。テクスチャは容量を考慮してWebPを優先する。

複雑なモデリング、任意メッシュ、頂点編集、ライティング編集、アニメーション編集、自動被写体分離、生成による背景補完は初期範囲に含めない。一度にすべて実装せず、段階ごとに検証・相談する。

## 2. 基本モデル（提案）

### カメラの役割

| 名前 | 役割 | 編集時の扱い |
| --- | --- | --- |
| 基準カメラ（projectionCamera） | 元画像を投影する位置と画角を定義 | 明示的な操作でのみ変更する |
| 表示カメラ（viewCamera） | レンダリングと視差確認に使用 | 基準カメラを初期値とし、位置・回転・FOVを変更できる |

表示カメラを動かしても投影は固定する。基準カメラへ戻して元画像との一致を確認できるようにする。基準カメラを変更した場合は投影とベイク結果を更新する。独立した作業用カメラは必要性を確認してから追加する。

Three.jsの右手系、Y-up、カメラ前方はローカル-Zを使う。位置・サイズは任意の共通シーン単位。回転のUI表示は度、順序はXYZを提案し、JSONではQuaternionで保存する。FOVは垂直方向の度数として入力し、GLB出力時にラジアンへ変換する。

### Plane

- 安定したID、名前、親、位置、回転、幅、高さ、マテリアル、投影対象画像を持つ。
- サイズは幅・高さで管理し、初期段階ではscaleを別の編集項目にしない。
- 通常Planeはワールド空間に配置する。初期の追加位置・サイズは検証段階で決める。
- Plane一覧から選択し、数値入力で編集する。ギズモやドラッグ編集は後段で検討する。
- 初期案では背景を含め最大9枚。上限で追加を抑止するかは未決定。
- 片面表示を初期案とし、裏側から見る必要が出た場合に両面表示を検討する。

### 背景Plane

表示カメラの子とし、ローカル-Z方向へ配置する案。表示カメラの移動・回転に追従し、通常Planeの後方を覆う。無限遠ではなく有限距離のPlaneとして扱う。

距離をd、垂直FOVをθ、アスペクト比をaとすると、画面を覆う最低サイズは `高さ = 2d × tan(θ / 2)`、`幅 = 高さ × a`。near/far、通常Planeの奥行きと整合させ、過度にfarを広げない。

基準状態の親変換を含めて背景への投影を計算し、その結果を背景ローカルのUVへ固定する案。以降は表示カメラへ追従しても再投影しない。常時ワールド座標から再投影すると、背景画像がカメラに対して固定されなくなるため、通常Planeと処理を区別する。

背景の距離・サイズを自動調整するか、FOV変更時に再フィットするか、手動値を優先するかは未決定。

## 3. 画像とCamera Projection（提案）

### 入力と画像比率

まず1枚のローカル画像を読み込み、すべてのPlaneで共有する。ブラウザー内で処理し、サーバーへのアップロードは行わない構成を提案する。

基準カメラのアスペクト比は元画像に合わせる。表示領域の比率が異なる場合は余白を設け、画像を引き伸ばさない。対応入力形式と最大画像サイズは最初の検証時に決める。

### 投影計算

Plane上の点を基準カメラのクリップ座標へ変換する。

```text
clip = projectionMatrix × viewMatrix × planeWorldMatrix × localPoint
ndc = clip.xyz / clip.w
imageUV = ndc.xy × 0.5 + 0.5
```

画像の上下方向はThree.jsのテクスチャ設定とベイク経路を合わせて決定し、上下左右に目印がある画像で確認する。基準カメラの背面、near/far外、画像UV範囲外は無効な投影として扱い、画像端を無制限に引き伸ばさない。

編集時は投影用シェーダーを一時利用する方式、または変更時にベイクを更新してMeshBasicMaterialで表示する方式を比較する。表示方式は未決定であり、GLBはどちらの場合も通常UVとテクスチャへ変換する。

Planeの四隅に投影UVを設定するだけでは、傾いたPlane上の透視投影が正確に再現されない場合がある。ベイクではPlaneのローカルUVごとに点を復元して投影画像をサンプルする方式を第一候補とする。

### 隠れた領域と切り抜き

1枚の完成画像だけでは、被写体の切り抜きや、その背後の画像は得られない。カメラ移動で画像の重複・背景の欠けが見える可能性がある。

最初は矩形Planeと共有画像だけで投影を検証する。実用上のレイヤー分離には、Planeごとの外部作成済みアルファマスク、または透過画像の入力が必要かを相談する。ツール内のマスク描画は初期範囲外。複数Planeへの投影は遮蔽を自動判定せず、それぞれ独立に行う案とする。

### 元画像との比較

最初は同一アスペクト比での左右並列表示を提案する。基準カメラで一致を確認し、表示カメラを動かして視差を確認する。重ね合わせ・差分表示は必要になった段階で追加する。

色比較のため、画像テクスチャのsRGB指定、レンダラー出力、トーンマッピング、アルファの扱いを統一する。初期案はトーンマッピングなし。完全一致を約束せず、フィルタリングやベイク解像度による差を検証する。

## 4. マテリアル（提案）

| モード | 編集時の基本設定 | GLB |
| --- | --- | --- |
| OPAQUE | MeshBasicMaterial、transparent=false、opacity=1、depthWrite=true | alphaMode=OPAQUE |
| BLEND | MeshBasicMaterial、transparent=true、depthWrite=false | alphaMode=BLEND |

BLENDのアルファは画像アルファとopacityの積を使う案。MASKは初期対象外。OPAQUEの投影範囲外は仮に黒、BLENDでは透明とし、範囲外を含むPlaneはUIで知らせる案とする。

透過Planeの交差や近接では描画順の問題が起きる。独自renderOrderやdepthWrite設定は一般的なGLBビューアーで同じように復元されるとは限らないため、それらへの依存を避けたシーンで検証する。

照明に依存しない見た目は、GLBでは標準拡張KHR_materials_unlitで表す。これは独自シェーダーではないが、ビューアーの対応確認が必要。[拡張仕様](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Khronos/KHR_materials_unlit/README.md)

## 5. JSON：編集データ（提案）

JSONを再編集の正本とし、GLBの再読み込みによる編集復元は初期範囲外とする。

| 項目 | 保存内容 |
| --- | --- |
| schemaVersion | データ形式のバージョン |
| assets | 画像ID、名前、MIME、画像データまたは参照、画像寸法 |
| projectionCamera | 位置、Quaternion、垂直FOV、aspect、near、far |
| viewCamera | 同上 |
| planes | ID、名前、親の種別、ローカル位置、Quaternion、幅、高さ、画像ID、投影設定、alphaMode、opacity |
| background | 対象PlaneのID、距離、フィット方針、投影時の基準変換 |
| exportSettings | ベイク解像度、画像形式、品質など |

投影設定は画像との対応、基準カメラ参照、UV範囲外の扱いを含む。背景を固定投影する場合は、その計算を再現できる変換も保存する。生成済みベイク画像はキャッシュとして扱い、原画像と設定から再生成できるようにする。

初期案では持ち運びしやすい単一JSONとし、元画像をData URLで埋め込む。Base64による容量増加があるため、大画像を扱う段階で別ファイル方式と比較する。Blob URLやローカル絶対パスのみを保存しても別セッションで復元できないため、それらには依存しない。

読み込み時はバージョン、ID参照、数値の有限性、正の幅・高さ、FOV範囲、near/farの前後関係、画像形式・サイズを検証する。不正データで編集中の状態を上書きしない。実際のスキーマと各値の上限は実装前に確定する。

## 6. GLB：表示用データ（提案）

### ベイクと出力

1. 出力時点の状態を複製し、Planeごとの通常UVに対応する画像を生成する。
2. 各テクセルのローカル位置を基準カメラへ投影して元画像の色・アルファを取得する。マスク対応時は同時に合成する。
3. ベイク画像をMeshBasicMaterialのmapへ割り当てる。UV原点、色空間、アルファ境界を確認する。
4. 通常Plane、背景Planeと親子関係、表示カメラを含むシーンをGLTFExporterのbinary出力でGLB化する。
5. 画像をGLB内に埋め込み、補助グリッド・ギズモ・投影シェーダーを含めず単体で読み込めるようにする。

背景は表示カメラの子として書き出す。基準カメラは編集専用として初期案ではGLBへ含めない。GLBには出力時の表示カメラの姿勢・画角を保持する。GLTFExporterはカメラとKHR_materials_unlit、EXT_texture_webpに対応するが、採用バージョンで生成結果を確認する。[Three.js公式ドキュメント](https://threejs.org/docs/pages/GLTFExporter.html)

glTFのカメラ格納と、ビューアーがそれを初期表示に選ぶことは別である。シーンの初期カメラを必ず指定できるとは扱わない。別の閲覧用カメラが使われた場合、背景は書き出したカメラに付いたままとなり、閲覧用カメラには追従しない。[glTF 2.0仕様](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#cameras)

### テクスチャ形式と容量

WebPを優先候補とする。glTF 2.0のWebPはEXT_texture_webpを使うため、WebPのみを格納するGLBは対応ビューアーが必要になる。PNG/JPEGのフォールバックを併記すると互換性を補えるが容量が増える。[EXT_texture_webp仕様](https://github.com/KhronosGroup/glTF/blob/main/extensions/2.0/Vendor/EXT_texture_webp/README.md)

出力方針は次の2案を比較して決める。

- 容量優先：WebP。対応ビューアーを明記し、非対応時はPNG/JPEGで再出力できるようにする。
- 互換性優先：透過画像はPNG、不透明画像はPNGまたはJPEG。WebP対応に依存しない。

ベイクは最初はPlaneごとの個別画像とし、アトラス化は後回し。最大解像度・WebP品質・アルファ境界・総容量を実測して初期値を決める。画面への投影サイズからの自動解像度調整は後段で検討する。

## 7. 段階的な検証計画

各段階を一つずつ実装し、結果と残課題を確認してから次へ進む。以下はロードマップ案であり、全段階の一括実装を意味しない。

| 段階 | 内容 | 確認すること |
| --- | --- | --- |
| 0：今回 | docsに仕様案と未決定事項を整理 | 次の検証範囲について合意する |
| 1：最小投影 | 画像1枚、固定の通常Plane 2枚、基準カメラ、表示カメラの数値操作、元画像との並列比較 | 基準位置での一致、移動時の視差、傾けたPlaneの投影、画像上下・色 |
| 2：編集と背景 | Plane追加・削除・数値編集、カメラ編集、背景、OPAQUE/BLEND | 遠近関係、背景追従、透過順、投影範囲外、9枚での操作感 |
| 3：JSON | 保存・読み込み、画像同梱、入力検証 | 別セッションで画像・両カメラ・背景・投影状態が復元される |
| 4：GLB | UVベイク、カメラ同梱、画像形式比較 | 専用シェーダーなしで再現、傾斜Planeの一致、容量、背景親子関係 |

段階1では編集UIの完成、背景、JSON、GLBは実装しない。まず投影方法の成立を確かめる。

GLB検証ではThree.js GLTFLoaderによる再読み込みに加え、別実装のビューアーを少なくとも1つ選定する。格納カメラを選んだ表示、独立カメラの表示、WebP対応、unlit、BLENDを確認し、互換性の範囲を記録する。ファイル構造はglTF Validatorでも確認する案とする。

## 8. 実装前に相談する項目

まず段階1の範囲とカメラ分離を確認し、それ以外は必要になる段階で決める。

1. **最小検証**：共有画像1枚と固定Plane 2枚から始めてよいか。
2. **カメラ**：固定投影用と視差確認用を分け、基準へ戻す操作を設ける方針でよいか。
3. **レイヤー分離**：矩形だけで足りるか、外部マスク・透過画像が必要か。
4. **背景**：表示カメラの子とし、基準状態で投影を固定するか。FOV変更時のフィット方法。
5. **保存**：単一JSONへの元画像埋め込みを採用するか。
6. **GLB互換性**：優先するビューアーと、WebP優先・PNG/JPEG優先の初期設定。
7. **制限値と操作**：最大画像寸法、ベイク解像度、上限枚数、入力範囲、ギズモの必要性。
